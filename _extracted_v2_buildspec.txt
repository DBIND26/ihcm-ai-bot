1. Product Definition
1.1  What this is
IHCM Operating Intelligence Platform is a secure internal web application that turns IHCM's fragmented operational knowledge into fast, trustworthy, role-aware decision support for facility, regional, and central teams.
It is not a chatbot. It is not five bots in a browser sidebar. It is the internal operating brain for a 7-building SNF operator scaling to 30+ buildings.
1.2  What it does
Gives fast, role-relevant answers grounded in IHCM's approved knowledge base
Generates first-draft operating documents: Plans of Correction, denial appeals, census plans, referral outreach letters
Retrieves approved playbooks, policies, and building-specific intelligence on demand
Compares facilities against goals, peers, and historical patterns
Captures institutional learning — successful interventions, resolved denial patterns, approved playbooks
Improves recommendations over time through governed feedback loops

2.3  Auth and middleware
Every route under app/(platform)/ is protected by middleware.js. Unauthenticated requests redirect to /login. Role is read from the profiles table and attached to the session on every request.
// middleware.js — runs on every (platform) request
import { createMiddlewareClient } from '@supabase/auth-helpers-nextjs'
import { NextResponse } from 'next/server'
export async function middleware(req) {
const res = NextResponse.next()
const supabase = createMiddlewareClient({ req, res })
const { data: { session } } = await supabase.auth.getSession()
if (!session) return NextResponse.redirect(new URL('/login', req.url))
return res
}
export const config = { matcher: ['/(platform)/:path*'] }

create policy "admin read all profiles" on profiles for select
using (auth.email() in (select email from auth.users where id in
(select id from profiles where role in ('corporate_admin','knowledge_manager'))));
-- Conversations: users see only their own
create policy "own conversations" on conversations for all using (user_id = auth.uid());
create policy "regional sees building convos" on conversations for select
using (exists (select 1 from profiles where id = auth.uid() and role in ('regional_operator','corporate_admin')));
-- Messages: inherit conversation access
create policy "messages via conversation" on messages for all
using (conversation_id in (select id from conversations where user_id = auth.uid()));
-- Knowledge: approved content visible to all, draft only to managers
create policy "approved knowledge public" on knowledge_sources for select
using (status = 'approved');
create policy "managers see all knowledge" on knowledge_sources for all
using (exists (select 1 from profiles where id = auth.uid() and role in ('knowledge_manager','corporate_admin')));
-- Building metrics: all authenticated users can read
create policy "read building metrics" on building_metrics for select using (auth.uid() is not null);
create policy "regional updates metrics" on building_metrics for insert
using (exists (select 1 from profiles where id = auth.uid() and role in ('regional_operator','corporate_admin','facility_admin')));
-- Audit events: write by service role, read by admins only
create policy "audit read admins" on audit_events for select
using (exists (select 1 from profiles where id = auth.uid() and role in ('corporate_admin','knowledge_manager')));

5. API Route Specifications
5.1  POST /api/chat
Main Q&A endpoint. Handles all Tier 1–3 requests. Tier 4 goes through /api/workflow.
// app/api/chat/route.js — request body shape
{
conversationId: string | null,   // null = start new conversation
buildingId: string | null,        // injects building context
message: string,                  // user's question
workflowType: string,             // default: 'ask'
}
Server-side logic:
Authenticate user via Supabase server client. Get role from profiles table.
Classify request tier using lib/ai/classify.js (keyword + pattern matching, no extra API call).
Retrieve building context: SELECT * FROM v_latest_building_metrics WHERE building_id = $1.
Retrieve relevant knowledge: full-text search on knowledge_sources WHERE status='approved', ranked by relevance.
Build system prompt: role prompt + building context from structured data + retrieved knowledge snippets + tier-appropriate suffix.
Call Anthropic API with assembled prompt and conversation history.
Store conversation and message in Supabase (create conversation if conversationId is null).
Write audit_event with all metadata.
Return response with sources_used array and risk_tier.
5.2  POST /api/workflow
Structured workflow endpoint for Tier 4 document drafting. Requires intake_data to be complete before calling Anthropic.
// Request body
{
workflowType: 'poc_draft' | 'appeal_draft' | 'census_plan' | 'building_comparison',
buildingId: string,
intakeData: object,   // workflow-specific required fields
}
Each workflow type validates its required intake fields server-side before any API call is made. Missing fields return 422 with a list of what's needed.
5.3  POST /api/knowledge/search
// Request
{ query: string, buildingId?: string, state?: string, sourceType?: string }
// Response
{ sources: [{ id, title, citation_text, effective_date, owner, relevance_score }] }
5.4  POST /api/feedback
{ messageId: string, rating: string, note?: string }
Writes to feedback_events. If rating is 'questionable' or 'saved', auto-creates a review_queue entry.
6. Knowledge Architecture
6.1  How building context works in V2
This is the most important architectural change from V1. Building context is no longer a hand-written prompt string. It is assembled at runtime from the building_metrics table — structured, versioned, and owned data.
// lib/knowledge/buildingContext.js
export async function getBuildingContext(buildingId, userRole) {
const metrics = await supabase
.from('v_latest_building_metrics')
.select('*')
.eq('building_id', buildingId)
.single()
if (!metrics.data) return null
const m = metrics.data
const ageDays = daysSince(m.refreshed_at)
const freshnessWarning = ageDays > 14 ? `[DATA ${ageDays} DAYS OLD — may be stale]` : ''
// Assemble role-specific context slice
const base = `Building: ${m.name} (CMS ${m.cms_provider_id}, ${m.state})
Census: ${m.census_current}/${m.census_licensed}. Trend: ${m.census_trend}.
Strategic priority: ${m.strategic_priority}. ${freshnessWarning}`
const byRole = {
mds_coordinator: `Skilled mix: ${m.skilled_mix_pct}% (target ${m.skilled_mix_target}%).
Top diagnoses: ${m.top_diagnoses?.join(', ')}. Payer mix: Medicare ${m.medicare_pct}%.`,
don: `Last survey: ${m.last_survey_date}. Open F-tags: ${m.open_ftags?.join(', ') || 'none'}.
Red QMs: ${m.red_qms?.join(', ') || 'none'}. OT: ${m.ot_pct}% (target ${m.ot_target}%).`,
facility_admin: `Census target Q2: ${m.census_q2_target}. Obstacle: ${m.census_obstacle}.
Top referral sources: ${JSON.stringify(m.top_referral_sources)}.
EBITDAR YTD: ${m.ebitdar_ytd} vs budget ${m.ebitdar_budget}.`,
regional_operator: `Admin: ${m.administrator_name} (${m.administrator_tenure_months}mo).
DON: ${m.don_name} (${m.don_tenure_months}mo).
Top worries: ${m.top_worries?.join('; ')}. ${m.recent_history}`,
}
return base + '\n' + (byRole[userRole] || '')
}
6.2  Knowledge retrieval function
// lib/knowledge/retrieve.js
export async function retrieveKnowledge(query, opts = {}) {
const { buildingId, state, sourceTypes, limit = 5 } = opts
let q = supabase
.from('knowledge_sources')
.select('id,title,citation_text,effective_date,full_content,source_type')
.eq('status', 'approved')
.textSearch('full_content', query, { type: 'websearch' })
.limit(limit)
if (buildingId) q = q.or(`building_id.eq.${buildingId},building_id.is.null`)
if (state) q = q.or(`state.eq.${state},state.is.null`)
if (sourceTypes) q = q.in('source_type', sourceTypes)
const { data } = await q
return data || []
}

7. Structured Workflow Specifications
These are the four T4 structured workflows for Phase 1. Each has a defined intake form, validation rules, system prompt template, output structure, and required caveats.
7.1  Plan of Correction (POC) workflow
Intake fields — all required
citation_tag — F-tag number (e.g. F689)
deficiency_summary — brief description of what was cited
immediate_jeopardy — boolean: was IJ declared?
current_mitigation — what has already been done since the survey
building_id — which building
citation_date — date of survey/citation
Output structure — required sections
Section 1: Immediate corrective actions (within 24/48/72 hours)
Section 2: Root cause analysis
Section 3: Systemic correction plan
Section 4: Monitoring and ongoing measurement plan
Section 5: Responsible owner and completion dates
Section 6: Assumptions made — what the system did not know
Banner: 'This draft requires review by a qualified healthcare compliance professional before submission to the state agency. Do not submit without review.'
System prompt template (abbreviated)
You are an expert SNF compliance advisor drafting a Plan of Correction for Independence Healthcare Management.
BUILDING CONTEXT:
{buildingContext}
CITED DEFICIENCY:
F-tag: {citation_tag}
Deficiency: {deficiency_summary}
Immediate jeopardy: {immediate_jeopardy}
Current mitigation: {current_mitigation}
RETRIEVED GUIDANCE:
{retrievedKnowledge}
Draft a complete Plan of Correction with all required sections. For every recommendation, note whether it is based on retrieved IHCM guidance or general best practice. Include an explicit assumptions section listing any information you did not have.
Do not express final compliance certainty. This is a first draft for professional review.
7.2  Denial / Appeal workflow
Intake fields — all required
payer — payer name (e.g. UnitedHealthcare MA, Arkansas DHS Medicaid)
denial_code — e.g. CO-96, CO-4, PR-96
denial_reason — plain text reason from EOB/remittance
service_dates — admission and denial date
auth_details — was auth obtained? Auth number if yes.
documentation_status — what clinical docs exist to support appeal
Output structure
Recommended next step (appeal vs. redetermination vs. reconsideration)
Appeal pathway with timeline and deadlines
Evidence checklist — specific documents to gather
Draft appeal letter (if requested)
Payer-specific notes from retrieved guidance
Assumptions section
7.3  Census Growth Plan workflow
Intake fields
building_id — auto-fills current census from metrics table
target_census — confirmed by user or pulled from metrics
timeframe_days — 30, 60, or 90
top_constraints — what's blocking growth right now (free text)
Output structure
Week-by-week milestone table
Priority referral actions with named targets from building profile
Discharge planner outreach list
Internal bottleneck checklist
Weekly scorecard metrics to track
7.4  Building Comparison workflow
Inputs
building_ids[] — 2 to 7 buildings to compare
focus_dimension — census | quality | staffing | financial | all
Output — mandatory elements
Comparative snapshot table with freshness dates shown for every metric
Largest performance gaps identified
Urgency ranking with rationale
Top 3 operator actions per building
Missing data called out explicitly — no silent gaps
